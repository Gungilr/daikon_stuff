# Stripped binaries keep the bytes, lose the nouns

Recovering types from a stripped x86-64 binary is hard because compilation keeps the *behaviour* of a program and throws away the *description* of its data. Names, typedefs, struct boundaries, signedness, the order of mixed int/float parameters and every field the code never touches leave no trace in the machine code. What survives is indirect: access widths, the opcodes that consume a value, and the library calls a value reaches ([Caballero & Lin survey](https://software.imdea.org/~juanca/papers/types_csur16.pdf); [TIE](https://users.ece.cmu.edu/~aavgerin/papers/tie-ndss-2011.pdf)). This project's own measurements fit that account closely. The black-box tracer watches exactly the same execution Kvasir does: sample counts are identical at **198 of 198 program points**. It makes **0 false claims in 6,717 audited facts**. Yet it matches only **1,255 of 5,419** Kvasir oracle facts (F1 24.2%), and **82.1% of its misses mention a variable it never declares** ([EVALUATION-KVASIR-SUITE.md](../docs/EVALUATION-KVASIR-SUITE.md); [phase11.md](../docs/plans/phase11.md); [score_diagnose.py](../scripts/score_diagnose.py)). Three binary-only type sources were tried as hints: one learned (ReSym) and two static (TypeForge, retypd). All three moved the score by **±0**. Even DWARF itself, fed in as hints, is worth only **+34 facts through parameter types**, **+235 through the struct layouts the run touched** and **+533 through full layouts**, nearly all of it via globals ([struct-hints.md](../docs/plans/struct-hints.md); [static-type-tools.md](../docs/plans/static-type-tools.md)). The gaps fall into three groups. Some are lost in principle and should come out of the scoring denominator: names, int/float interleaving, untouched objects, and shapes that compile to identical code. Some are recoverable but unsolved, chiefly global layouts and by-value structs. A small, cheap group are defects in this tracer's own value reporting (float returns, strings, poison values), which the soundness audit cannot see. The next steps should follow that order of value: fix the defects, attack globals, then build a corpus where coverage and optimization actually bite.

## Compilation erases names and keeps type only where an instruction consumes it

The surveys agree on the starting point. Once compiled, data lives "in untyped CPU registers and memory", so a recovery tool must first rebuild variables (offset plus size) and only then assign types ([Survey](https://software.imdea.org/~juanca/papers/types_csur16.pdf)). TIE notes that a register is easily seen to hold 32 bits but that it is "difficult to infer high-level types such as signed integers, pointers, unions, and structures" ([TIE](https://users.ece.cmu.edu/~aavgerin/papers/tie-ndss-2011.pdf)). The erased facts sort into three tiers by how much fingerprint they leave.

**Names and typedefs leave no fingerprint at all.** Identifiers, field names and typedef names are "completely discarded in stripped binaries" ([ReSym](https://www.cs.purdue.edu/homes/lintan/publications/resym-ccs24.pdf)). A typedef's representation is identical to its parent type, so it "can only be distinguished … by how [it is] used", and no surveyed work targets typedef recovery ([Survey §5.6](https://software.imdea.org/~juanca/papers/types_csur16.pdf)). Learned systems guess names from corpus priors. Their accuracy on code outside the training set is the honest measure: ReSym gets 37.5% of names and 49.9% of types right not-in-train, against more than 85% in-train ([ReSym](https://www.cs.purdue.edu/homes/lintan/publications/resym-ccs24.pdf)), and GenNm gets 17.3–22.8% on names never seen in training ([GenNm](https://arxiv.org/html/2306.02546v4)). This project's local ReSym reproduction shows the same failure mode. It reached 66.5% exact types on ReSym's own test data, and its errors were dominated by invented project-specific names (`int` predicted as a project type name, `hashtab*` as `hashmap_t*`). An evidence filter built from the binary caught 22.9% of wrong answers, but "it cannot fix the exact type … ReSym's main error is the type NAME, which no instruction or trace reveals" ([RESYM-LOCAL.md](../docs/RESYM-LOCAL.md)). The tracer emits `arg0`, `arg0[].off4` and `g_0x404060`. The scorer maps these onto Kvasir's names using DWARF at scoring time only ([score_invariants.py](../scripts/score_invariants.py)), so names themselves cost no points. But the mirror problem remains: **65.9% of the tracer's unmatched facts are about nouns Kvasir does not have** ([score_diagnose.py](../scripts/score_diagnose.py)).

**Signedness, pointer-ness, char/bool/enum and the pointee type leave a weak fingerprint.** Each shows up only if a type-revealing operation happens to touch the value. Few instructions "truly manifest signedness" ([Yan & McCamant](https://conservancy.umn.edu/items/8f4f4066-68bd-4bd5-9fcc-3fae77a53821)): add, sub, low-half multiply, bitwise operations, equality tests and plain moves are identical for `int` and `unsigned`. Pointers and integers share arithmetic, and "we only know that a particular register holds a valid address when it is dereferenced" ([Howard](https://www.ndss-symposium.org/wp-content/uploads/2017/09/slow.pdf)). A zero "could be both integer or NULL pointer" ([Survey §5.1](https://software.imdea.org/~juanca/papers/types_csur16.pdf)). `char` and `bool` collapse into one-byte integers, and `enum` sits in the same ABI class as `int` ([SysV ABI](https://math-atlas.sourceforge.net/devel/assembly/abi_sysV_amd64.pdf)).

Static decompilers paper over this by guessing. Hex-Rays reports "an identified variable as a signed integer" by default ([TIE](https://users.ece.cmu.edu/~aavgerin/papers/tie-ndss-2011.pdf)), and IDA often types 64-bit pointers as `__int64` ([Li et al.](https://arxiv.org/html/2503.07243v2)). This project measured Ghidra on ReSym's 94 test binaries. Ghidra's parameter types were fully exact for only about 22% of 44,366 parameters, and it was confidently wrong about the *kind* for 22%, mostly by calling a pointer `long` (8,977 cases). A simple binary-evidence checker caught **86.2% of those pointer-as-integer errors** and cut wrong-kind parameters from 22.9% to 4.5% ([rea-type-checker.md](../docs/plans/rea-type-checker.md)). Kind, in other words, is recoverable from evidence when the evidence exists. The tracer's phase-11 layout recovery confirms this: **kind accuracy 100% (141 of 141)**. That figure came only after a rule that an 8-byte slot holding nothing but 0 abstains, because "NULL and 0L read alike" ([phase11.md](../docs/plans/phase11.md)). Signedness has no such rescue. A never-shifted or never-compared `unsigned` with its high bit set reads back negative ([TOOL.md](../docs/TOOL.md)). The project estimates this "information-theoretic residue" — doubles never used as doubles, unsigned values never consumed as unsigned — at **roughly 5% of the oracle** ([phase10.md](../docs/plans/phase10.md)).

**Access width, float versus integer, and code pointers leave a strong fingerprint**, but even these have exceptions. Vectorization puts integer data in SSE registers, and IDA in OSPREY's gzip example misread a `movdqa`/`movups` copy as a 128-bit float field and produced a spurious union ([OSPREY](https://par.nsf.gov/servlets/purl/10296833)). The tracer met the same trap from the other direction. Typing `.rodata` made the literal `3.45` a double, and Daikon's fuzzy float equality then asserted `arg1 == g_0x402018`; the audit caught it ([phase11.md](../docs/plans/phase11.md)). A static SSE scan for double-typed globals found **zero** hits because `GlobalTest` never loads `globalDouble` as a double ([phase10.md](../docs/plans/phase10.md)). When no instruction says "double", there is nothing to find.

## Aggregate shapes collapse into identical access patterns

The deepest structural ambiguity is that different composite types compile to identical code. TypeForge puts it directly: `dereference(base + offset)` "could originate from either structure member accesses or array element accesses" ([TypeForge](https://noobone123.github.io/papers/typeforge-sp25.pdf)). Tools fall back on the heuristic that arrays "are more commonly processed in loops" ([Survey §5.3](https://software.imdea.org/~juanca/papers/types_csur16.pdf)). Howard refuses to call anything an array unless at least four elements are accessed in a loop. It also concedes that a field followed by an array, accessed in sequence, "is impossible to classify correctly solely based on memory access patterns" ([Howard](https://www.ndss-symposium.org/wp-content/uploads/2017/09/slow.pdf)). The rule that holds in principle is this: **two typings cannot be told apart when the program compiles to the same machine code under both**. Examples are `struct {int a,b;}` versus `int[2]`, `struct S*` versus a pointer to its first member ([Retypd §2.4](https://arxiv.org/pdf/1603.05495)), and a union versus whichever member is used.

The tracer runs into each of these ambiguities on the Kvasir suite. In ArrayTest's `returnIntSum(int a, int* b)`, the tracer recovered all six values of `b[]` exactly and then described them as six struct fields `arg1[].off0..off20`. As the evaluation puts it, "we recovered the array perfectly and then described it as a struct, so of the three oracle facts we match one and contribute six unmatched ones." The array sat on the stack, with no length argument and no malloc record, so the array model correctly abstained ([EVALUATION-KVASIR-SUITE.md](../docs/EVALUATION-KVASIR-SUITE.md)). NestedStructVarList's `counters[]` is touched only at constant indices 0, 5 and 9, which is "byte-for-byte a struct with three `int` fields at +0/+20/+36", below Howard's threshold; "calling it an array would be a guess" ([phase11.md](../docs/plans/phase11.md)).

Globals are worse. They are reached through RIP-relative absolute addresses with no base pointer ([Survey §4.5](https://software.imdea.org/~juanca/papers/types_csur16.pdf)). "An `int[18]` and eighteen adjacent `int`s produce identical access evidence", so only `.symtab`, which stripping removes, separates them ([phase9.md](../docs/plans/phase9.md)). Three attempts at struct-shaped globals scored **0 of 8 structs** right against DWARF, because "a statically-initialised struct is never written at run time" while an int array copied 8 bytes at a time *does* show mixed widths ([phase10.md](../docs/plans/phase10.md)).

**Unions** are an unsolved problem across the field. No surveyed tool fully supports them, and an untagged union is fundamentally hard to tell apart from a type conflict ([Survey §5.7](https://software.imdea.org/~juanca/papers/types_csur16.pdf)). Howard reports a merge of the member layouts ([Howard](https://www.ndss-symposium.org/wp-content/uploads/2017/09/slow.pdf)), and TIE "simply declares a union" whenever VSA over-approximation produces overlaps ([OSPREY](https://par.nsf.gov/servlets/purl/10296833)). The tracer abstains on the one union it met ([phase11.md](../docs/plans/phase11.md)).

**Wide copies** blur field boundaries in the other direction: memcpy-style word strides make a struct look like many 4-byte fields ([Howard](https://www.ndss-symposium.org/wp-content/uploads/2017/09/slow.pdf)). The tracer's **invented-field rate of 5.1% (9 of 176)** comes entirely from this. The cases are 8-byte loads copying a struct in crazy-test-1 and md5, and zeroing stores over `char` members, and "nothing at run time separates such a copy from a real 8-byte field" ([phase11.md](../docs/plans/phase11.md)).

**Untouched fields** are the hardest limit of all. Every access-based method "can only recover fields that the program accesses (or accessed in an execution for dynamic approaches)" ([Survey §4.5](https://software.imdea.org/~juanca/papers/types_csur16.pdf)). TypeForge lists never-accessed members as unrecoverable ([TypeForge](https://noobone123.github.io/papers/typeforge-sp25.pdf)), and learned systems show the signature of the same limit. ReSym's layout precision is 72.9% but its recall only 28.9%, and Idioms' best structural accuracy on realistic types is 15.1% ([ReSym](https://www.cs.purdue.edu/homes/lintan/publications/resym-ccs24.pdf); [Idioms](https://arxiv.org/html/2502.04536v2)).

The project's DWARF ceilings put a number on this limit. Supplying full struct layouts adds 533 matched facts. Supplying only the fields the run touched adds 235. The difference — roughly **+297 facts — is "untouched fields … No binary-only source can know those"** ([struct-hints.md](../docs/plans/struct-hints.md)). NestedStructTest is the extreme case: 560 of its 677 oracle facts are about `globalBetterFoo`, which the program never touches, so about 117 is "the most any black-box tracer can reach" ([phase11.md](../docs/plans/phase11.md)). Where memory *is* touched, the tracer is close to its ceiling: **layout F1 0.897 (P 94.9%, R 85.1%)** on 89 typed sites. That compares well with TypeForge's own reported 89.4% layout F1 at -O0 ([phase11.md](../docs/plans/phase11.md); [TypeForge](https://noobone123.github.io/papers/typeforge-sp25.pdf)).

## The calling convention scrambles interfaces before optimization even starts

The System V ABI maps parameters onto two independent register sequences, integers to `rdi, rsi, rdx, rcx, r8, r9` and floats to `xmm0–xmm7`, each with its own counter. It splits small aggregates into eightbytes: the ABI's own example packs two `int` fields of a struct into `%rdx` and sends its `double` to `%xmm0`. It passes structs larger than 16 bytes in memory, and returns large structs through a hidden pointer in `%rdi` ([SysV ABI 0.95](https://math-atlas.sourceforge.net/devel/assembly/abi_sysV_amd64.pdf)). Three consequences follow. First, `f(int a, double b, int c)` and `f(int a, int c, double b)` produce identical callee code, so **int/float interleaving is unrecoverable**. Second, a `{int,int}` struct in one register is a `long`. Third, a MEMORY-class return looks like an extra leading pointer parameter. All three are inferences directly from the classification rules.

The project measured each consequence. **By-value structs give the wrong arity in all 6 of 6 functions**. `baz(struct foo f)` shows 18 parameters, because a 252-byte argument read a word at a time "becomes eighteen", and `arg8 == 4614256650576692846L` is in fact the struct's `double c = 3.14159`. Others show zero. One crashed the tracer's finalizer with an `IndexError` (32 stack probes against a limit of 12) ([EVALUATION-KVASIR-SUITE.md](../docs/EVALUATION-KVASIR-SUITE.md); [TOOL.md](../docs/TOOL.md)). By-value struct fields account for **~370 missed facts** and are not modelled at all ([struct-hints.md](../docs/plans/struct-hints.md)).

Float parameters were invisible at tier 7 (8 of 8). Tier 9 made them visible, but this "is a genuine trade". FloatTest recall rose from 24% to 35%, while everything else lost 12 facts, because "nothing in the machine code records how they interleaved … Integer-first is a convention, not a recovery" ([phase9.md](../docs/plans/phase9.md)). The resulting **184 missed facts on float/int parameter order** are classed as unrecoverable "by anyone" ([resym-hints.md](../docs/plans/resym-hints.md)). Overall, use-before-def arity is exact on **81 of 99 functions**, and all 18 failures are by-value structs, floats or knock-on effects ([EVALUATION-KVASIR-SUITE.md](../docs/EVALUATION-KVASIR-SUITE.md)).

Unused parameters are invisible at the callee by construction, and decompilers drop them. The project found that **Ghidra shows no parameters for 31 of 79 reached functions that have them**. `void bar(struct foo *f) {}` decompiles as `void FUN_00401136(void)` ([struct-hints.md](../docs/plans/struct-hints.md)). This alone cost ReSym 11 facts of a DWARF pipe test before it predicted anything. Every learned tool that consumes decompiler output inherits this loss.

Compiler optimization layers more damage on top, and the literature is explicit that this suite does not yet exercise it. Optimizations "take well-typed machine code and produce functionally equivalent but ill-typed results". Examples are shared zero constants, stack-slot reuse "even … for formal-in parameters", and early-return value reuse ([Retypd §2.1](https://arxiv.org/pdf/1603.05495)). SROA turns non-escaping structs into unrelated SSA scalars, so no memory object remains ([LLVM SROA](https://llvm.org/doxygen/SROA_8cpp_source.html)). `-fipa-sra` removes unused parameters or passes only the used fields ([GCC](https://gcc.gnu.org/onlinedocs/gcc/Optimize-Options.html); [LWN](https://lwn.net/Articles/1073762/)). Lin & Gao list further callee-side signature violations at -O2: unread arguments, variadic functions that look normal, `rdx` read for a two-register return, and `push`/`lea` width promotion ([Lin & Gao](https://dbgao.github.io/oakland21.pdf)). TypeForge's layout recall falls from **82.2% at -O0 to about 31% at -O2/-O3** ([TypeForge](https://noobone123.github.io/papers/typeforge-sp25.pdf)).

Kvasir requires `-O0` and is "definitely incompatible with -fomit-frame-pointer" ([Daikon manual](https://plse.cs.washington.edu/daikon/download/doc/daikon.html)), so every number in this project is an -O0 number. That is the regime where access patterns are most faithful. The tracer's results are therefore an optimistic bound for real binaries, not a pessimistic one.

## Aliasing, cross-function flow and coverage decide which objects exist at all

Static tools must work out which object an address belongs to. Value-set analysis is sound but "conservative and hence leads to a large amount of bogus data-flow" and does not scale ([OSPREY](https://par.nsf.gov/servlets/purl/10296833)). Retypd sidesteps it by tracking only the stack pointer ([Retypd §2.7](https://arxiv.org/pdf/1603.05495)). Stack structs addressed by frame offset "become indistinguishable" from separate locals ([Survey §4.5](https://software.imdea.org/~juanca/papers/types_csur16.pdf)), and Ghidra "does not even group the two stack offsets to a structure" ([OSPREY](https://par.nsf.gov/servlets/purl/10296833)). Dynamic tools see concrete addresses and need no alias analysis, but "a missing base pointer is of course a fundamental limitation, as we cannot recognize what is not there" ([Howard](https://www.ndss-symposium.org/wp-content/uploads/2017/09/slow.pdf)).

**Cross-function flow** is how a pointer that a function merely passes along gets a type, and every system is weak here. A parameter the callee never uses "yields no capabilities" in retypd ([Retypd](https://arxiv.org/abs/1603.05495)). TYGR is purely intra-procedural; it names caller/callee patterns as its key missing ingredient and plateaus near 80% because "some variable types cannot be effectively differentiated by only observing how the variables are used" ([TYGR](https://www.usenix.org/system/files/usenixsecurity24-zhu-chang.pdf)). About 44.4% of variables propagate across functions ([Li et al.](https://arxiv.org/html/2503.07243v2)).

The project located the parameter-type headroom precisely. IntTest holds +31 of the +33 parameter-type gain in the DWARF pipe test, and `u` (an `int*`) alone is worth **+28**. But `returnIntSum` only null-checks `u` and passes it on. ReSym answered `void*`, "which is what the code supports". Retypd answered `char1_t[4]`, because "the array is on `main`'s stack, and the plugin's constraint generator does not model stack memory or address-taken locals. The one fact retypd was chosen for never reaches its solver" ([struct-hints.md](../docs/plans/struct-hints.md); [static-type-tools.md](../docs/plans/static-type-tools.md)). The tracer's own attempt to borrow evidence from the caller (`--infer-from-caller`) cost 22 points of precision for 3 of recall on the project's own corpus, because "nothing observable bounds a stack object" ([TOOL.md](../docs/TOOL.md); [EVALUATION-KVASIR-SUITE.md](../docs/EVALUATION-KVASIR-SUITE.md)). Functions such as `bazMapPtr(struct map* m) { return 500; }` exist in the suite precisely to test DWARF-driven traversal: Kvasir reports 21 facts and the tracer 1.

**Library anchors** are the main source of near-ground-truth types in stripped binaries. `strlen`, `strcpy` and some 2,016 libc functions type the values that reach them, which is why REWARDS uses library calls as type sinks ([REWARDS](https://www.cs.purdue.edu/homes/xyzhang/Comp/ndss10.pdf); [Survey §4.4](https://software.imdea.org/~juanca/papers/types_csur16.pdf)). But anchors propagate only along data flow, and libc's `void*` APIs are polymorphic ([Retypd §2.2](https://arxiv.org/pdf/1603.05495)). Most fields of application structs never reach a typed call. The Kvasir suite's test programs are deliberately self-contained, so anchors contribute little beyond the 90 `char*`-as-string misses that a `strlen`-style sink or rodata reading could resolve. The `--rodata-strings` option added 26 matched facts ([phase10.md](../docs/plans/phase10.md); [phase11.md](../docs/plans/phase11.md)).

**Uninitialised memory** is a description problem, not an observation problem. Kvasir prints "nonsensical" for values that cannot be evaluated, using Memcheck's per-bit validity, because "outputting nonsense values can degrade invariant detection" ([Daikon developer manual](https://plse.cs.washington.edu/daikon/download/doc/developer.html); [Valgrind](https://valgrind.org/docs/manual/mc-manual.html)). The tracer approximates this with a `0xAB` poison fill, so "a genuine `0xABABABAB` is misread". Its `--shadow` mode tracks only the heap, as Kvasir does, and comes out 15 matched facts *worse* ([TOOL.md](../docs/TOOL.md); [phase11.md](../docs/plans/phase11.md)).

**Coverage** is the classic weakness of dynamic recovery. Howard exercised only 50–71% of functions even with KLEE ([Howard](https://www.ndss-symposium.org/wp-content/uploads/2017/09/slow.pdf)). TIE showed that single-trace results can be "different and incompatible" across inputs, and that static analysis "is about as precise as REWARDS but can type 100% of all variables" ([TIE](https://users.ece.cmu.edu/~dbrumley/pdf/Lee,%20Avgerinos,%20Brumley_2011_TIE%20Principled%20Reverse%20Engineering%20of%20Types%20in%20Binary%20Programs.pdf)). On this suite, coverage is the one problem that does *not* bite. The programs are small -O0 tests in which every access executes, so "static analysis of `-O0` test programs sees nothing the run does not" ([static-type-tools.md](../docs/plans/static-type-tools.md)).

That explains the static tools' **±0** directly. TypeForge produced layouts for only 3 parameters and left 39 of its 54 fields untyped. Retypd's fields came out mostly `char1_t[k]`. Ghidra p-code static layouts agreed with the run on 22 of 36 parameters and added **0 fields** ([static-type-tools.md](../docs/plans/static-type-tools.md); [phase11.md](../docs/plans/phase11.md)). ReSym's ±0 has the same root cause, seen through a model: "ReSym and the tracer read the same evidence: how the code uses a value. Where the code dereferences a pointer, ReSym can be right, but the run has already shown the tracer the same thing … Where the code does not touch the pointer … ReSym has nothing to read either" ([struct-hints.md](../docs/plans/struct-hints.md)). On ReSym's own corpus, by contrast, the tracer reached only 680 of 30,865 parameter answers (2%) from `main` with no input ([RESYM-LOCAL.md](../docs/RESYM-LOCAL.md)). That is where coverage, and therefore static or learned help, would matter.

### Lost in principle

Five gaps cannot be closed by any binary-only method, whether dynamic, static or learned, because the information is not in the binary: names and typedefs, int/float parameter interleaving (184 facts), fields and objects the program never touches (about 297 facts of the full-layout ceiling, plus most of NestedStructTest), shapes that compile to identical code (uniform structs versus arrays, adjacent globals versus aggregates, unions, wide copies over narrow fields), and signedness or float-ness without a consuming opcode (about 5%). Learned models can *guess* the first and fourth from priors. But this project's ReSym runs show that on out-of-distribution, context-poor input the guesses do not survive contact with the run: 3 argument effects were applied and 10 refuted, and 2 layouts applied against 6 refuted ([struct-hints.md](../docs/plans/struct-hints.md)).

### Recoverable but unsolved

These gaps have evidence in the binary or the run, but no tool tried here turns it into Kvasir's vocabulary.

**Globals** are the largest pool by far: 3,396 of the 4,163 misses. The DWARF ceilings show where the value lies. Layouts delivered through parameters alone are worth only +40 (touched fields) to +128 (full). Adding globals raises this to +235 and +533. So **roughly three-quarters to four-fifths of the layout headroom (195 of 235 touched, 405 of 533 full) sits outside parameters, overwhelmingly in globals**, which a function-local, use-driven predictor like ReSym or TYGR does not even look at ([struct-hints.md](../docs/plans/struct-hints.md); [TYGR](https://www.usenix.org/system/files/usenixsecurity24-zhu-chang.pdf)).

**By-value structs** (~370 facts) are partly recoverable. ABI classification fixes the eightbyte boundaries, and caller-side copies reveal the extent of MEMORY-class structs.

**Pass-through pointers** are recoverable only if a caller-side object can be bounded. That is exactly what failed with `--infer-from-caller`.

**Exact definedness** needs shadow memory that also covers the stack, not just the heap.

Two problems belong in this column, but the suite cannot measure them: **coverage** and **optimization**. They are the regime in which static tools would actually pay off, and no corpus with an oracle has yet tested them.

### This tracer's own defects

The remaining gaps are errors in this tracer, not limits of the binary, and they are the cheapest to close.

**Float returns are wrong in every float-returning function the suite reaches (10 of 10).** At EXIT, the first float argument is restored into the `xmm0` slot, and the return value is then read from that same slot. So `doubleSub(15, -5246.54)` records `return = 15.0`, and Daikon reports `a == return` ([struct-hints.md](../docs/plans/struct-hints.md)).

**Float formatting differs from Kvasir's.** Kvasir prints `100.345001`; the tracer prints `100.34500122070312`. The values agree, but the text does not, so these facts fail to match.

**By-value structs crash the finalizer**, as described in the calling-convention section.

**IntTest's `returnIntSum` shows several value errors.** These come from a value-level comparison prototype that is not yet written up in the repository:
- the string `str` is printed as a raw address;
- the `float*` pointee is printed as an address;
- the poison value -1414812757 (`0xABABABAB`) is printed where Kvasir says uninitialised;
- the `0xDEADDEAD` pointer return is printed as 2.718, because the function was judged to return a double.

Each of these defects is a type error in disguise, and **the soundness audit is blind to all of them** because it checks facts against the tracer's own samples. History shows the same class has occurred before: argument values were once re-read from clobbered registers at EXIT ([plans/README.md](../docs/plans/README.md)).

The oracle has blemishes of its own as well. Kvasir's `is_param` flag makes Daikon drop non-unit coefficients, which makes 3 of 172 own-corpus facts false. And Daikon's own authors run the suite's larger programs with `--ignore-globals` or `--nesting-depth=1` ([EVALUATION.md](../docs/EVALUATION.md); [EVALUATION-KVASIR-SUITE.md](../docs/EVALUATION-KVASIR-SUITE.md)).

One honest uncertainty remains open. Even with full DWARF layouts, 3,631 oracle facts stay unmatched (F1 34.6%). The notes do not break that residue down beyond the category counts above, so how much of it is declaration and object identity, and how much is presentation and form, is not yet measured.

## Conclusion

The central lesson is that this suite measures **vocabulary, not vision**. The tracer sees everything Kvasir sees, asserts nothing false, and recovers touched layouts at F1 0.897. What it lacks is the source-level description Kvasir reads from DWARF. Much of that description is gone in principle, and the part that is not gone lives mostly in globals, not in the parameters that every learned and static type tool targets. That is why three state-of-the-art type sources scored ±0. They are not weak tools. They answer a question — "what is this parameter's type?" — that is worth at most +34 facts here, and on fully executed -O0 code they read exactly the evidence the run already has. Their comparative advantage, coverage of unexecuted and optimized code, is precisely what this corpus never exercises.

For scoring, this argues for reporting recall against a **reachable denominator**. That means removing the oracle facts that no binary-only method can produce: untouched objects and fields, int/float interleave order, and facts that hinge on codegen-equivalent shapes. Scored that way, the tracer's real gap is visible apart from Kvasir's DWARF advantage. Following TIE, the scoring should also accept equivalence classes ("struct of three ints" is as right as `int[3]` when the code is identical). It should also add a **value-level comparison** against Kvasir's traces, since that comparison, not the soundness audit, is what finds this tracer's defects. For next steps, the order follows the payoff. First fix the float-return, formatting and value-printing defects: they are certain, cheap gains. Next, treat global layouts as the main recovery problem, because globals hold most of the oracle and most of the ceiling. Only then return to static or learned hints, and do so on a corpus built to give them something to contribute: optimized builds, low dynamic coverage, and a DWARF oracle of their own.
