# Give the fuzz loop a real bug detector

Our loop missed the `abs_diff` overflow because it has no **bug oracle**, meaning no component whose job is to say "this run did something wrong". It only had Daikon's guesses about normal behaviour, and Daikon never guessed `return >= 0`. The fix is to stop relying on learned invariants to *detect* bugs and add oracles that fire on their own. In source mode, that means replaying inputs on a second build compiled with UndefinedBehaviorSanitizer (UBSan). There is one catch we verified locally: **gcc silently drops the overflow check when `-fwrapv` is on**, so that oracle build must leave `-fwrapv` out. In blackbox mode, it means reading the CPU's overflow flag (OF) right after each `add`/`sub`/`imul`, and turning off the lazy memory mapping that currently hides every wild pointer. Two cheaper additions cover the bugs no sanitizer defines. One is a "never forget" anomaly profile on return values, in the style of DIDUCE and CBI, which would have flagged the first negative `abs_diff` result with no invariant template at all. The other is an AFL-HR-style "headroom" distance, which pushes the fuzzer toward arithmetic that is close to overflowing. The literature also warns about the cost: **most integer overflows seen at runtime are intentional, not bugs** (hashes, random number generators, overflow checks), so raw overflow alarms need tiering and filtering. Otherwise the blackbox mode will drown in false alarms.

## The loop saw the bug five times but had nothing to report it with

Some vocabulary first. A fuzzer has two separate jobs. **Guidance** decides which inputs are worth keeping and mutating. The **oracle** decides whether an input exposed a bug. Fuzzing surveys define the bug oracle as the part that checks whether an execution violates a security policy ([Manès et al.](https://arxiv.org/pdf/1812.00140)). Mainstream fuzzers keep the two channels apart. AFL++ puts "test cases for every distinctive execution path" in `queue/`, and only inputs that make the program "receive a fatal signal (e.g., SIGSEGV, SIGILL, SIGABRT)" in `crashes/` ([AFL++ docs](https://github.com/AFLplusplus/AFLplusplus/blob/stable/docs/afl-fuzz_approach.md)). For bugs that do not crash, AFL++'s advice is to make the target call `abort()` when a sanity check fails ([AFL++ in-depth guide](https://github.com/AFLplusplus/AFLplusplus/blob/stable/docs/fuzzing_in_depth.md)), or to set `AFL_CRASH_EXITCODE` so that a chosen exit code counts as a crash ([AFL++ env vars](https://github.com/AFLplusplus/AFLplusplus/blob/stable/docs/env_variables.md)).

Our loop has only a crash oracle plus Daikon. With `-fwrapv`, `2147483647 - (-5)` is *defined* to wrap around to `-2147483644`. Nothing crashes and nothing signals, so the crash oracle cannot fire, and recording a refuted invariant was the only remaining path. The standard survey of the "test oracle problem" files Daikon under **derived oracles**, describing it as "an unsound test oracle that gathers likely invariants" in which "only those likely invariants remain that no observation invalidates" ([Barr et al., TSE 2015](https://discovery.ucl.ac.uk/id/eprint/1471263/1/06963470.pdf)). A derived oracle can only defend properties it has already inferred. A single seed returned one value, so Daikon proposed things like `return == 2`. Once fuzzing produced varied, partly negative returns, `return >= 0` was never true of the whole corpus, so it was never proposed. The authors of ClearView, which ran a Daikon variant on x86 binaries, list the same two limitations: the preconfigured invariant set may lack the needed invariant, and "the learning phase may not provide enough coverage … to learn this invariant" ([Perkins et al., SOSP 2009](https://rcs.uwaterloo.ca/~ali/cs842-s23/papers/autopatch.pdf)).

The published systems that work point the same way. ClearView did **not** use invariants to detect attacks. It used separate monitors that have "no false positives" and consulted invariants only afterwards, to locate and patch the fault. It blocked all 10 Red Team exploits and patched 7 ([same paper](https://rcs.uwaterloo.ca/~ali/cs842-s23/papers/autopatch.pdf)). Carrot tried pure Daikon-style invariants for fault localization and "could not locate any bugs" in Siemens-suite programs ([Pytlik et al., 2003](https://arxiv.org/pdf/cs/0310040)). InvsCov, the closest published cousin of our loop, compiled Daikon invariants into a fuzzer but used violations only as *guidance*. ASan and UBSan were its bug oracles ([Fioraldi et al., USENIX Sec 2021](https://www.usenix.org/system/files/sec21-fioraldi.pdf)). The lesson for us is that invariants are good for steering and explaining, and a precise oracle has to do the reporting.

## Sanitizers catch abs_diff exactly, but only in a build without -fwrapv

A **sanitizer** is a compiler option that inserts run-time checks into the program. UBSan's `signed-integer-overflow` check fires when "the result of a signed integer computation cannot be represented in its type", including `INT_MIN / -1`. Clang states that UBSan "is not expected to produce false positives" and that the checks have "small runtime cost" ([Clang UBSan docs](https://clang.llvm.org/docs/UndefinedBehaviorSanitizer.html)). For a number, the precursor tool IOC measured a **44% mean slowdown** for undefined-behaviour integer checks on SPEC CPU2006, with a range of −0.5% to 191% ([Dietz et al., ICSE 2012](https://users.cs.utah.edu/~regehr/papers/overflow12.pdf)). That is negligible next to Kvasir running under Valgrind.

The problem is the interaction with `-fwrapv`. Clang's current documentation says "checks are still added even when `-fwrapv` is enabled" ([Clang UBSan docs](https://clang.llvm.org/docs/UndefinedBehaviorSanitizer.html)), and GCC's documentation does not address the question ([GCC Instrumentation Options](https://gcc.gnu.org/onlinedocs/gcc/Instrumentation-Options.html)). The local tests recorded in our research notes (gcc 13.3.0, clang 18.1.3, using `abs_diff(2147483647, -5)`) found the following. Under gcc without `-fwrapv`, the oracle printed `runtime error: signed integer overflow: 2147483647 - -5 cannot be represented in type 'int'` and exited 1. **With `-fwrapv` added, the same build printed `-2147483644` and exited 0.** Clang 18 in trap mode also dropped the check under `-fwrapv`, so the documented clang behaviour must come from a later release; we did not pin down which one. gcc's older `-ftrapv` does abort, but only when it comes *after* `-fwrapv` on the command line, because the last flag wins. In practice, any build we want to catch overflow with must not contain `-fwrapv`. At `-O0` that is harmless, because the check runs before any optimisation could exploit the undefined behaviour.

To turn a sanitizer report into a fuzzer verdict, the process has to die or exit non-zero. By default, gcc keeps running after a report, and "the exit code may still indicate success". `-fno-sanitize-recover=` makes the program exit non-zero after the first error, and `-fsanitize-trap` executes a trap instruction ([GCC docs](https://gcc.gnu.org/onlinedocs/gcc/Instrumentation-Options.html)). OSS-Fuzz, Google's continuous fuzzing service, is the industry reference configuration. It makes `signed-integer-overflow`, `shift` and `integer-divide-by-zero` fatal, and it enables `unsigned-integer-overflow` but leaves it recoverable, so unsigned wraparound is logged and does not abort the run ([OSS-Fuzz base-builder](https://raw.githubusercontent.com/google/oss-fuzz/master/infra/base-images/base-builder/Dockerfile)). gcc does not offer unsigned-overflow or implicit-conversion checks at all; our local test showed gcc 13.3 rejects them, and they exist only in clang. For memory bugs in the same replay build, ASan's typical slowdown is 2x and it is likewise "not expected to produce false positives" ([Clang ASan docs](https://clang.llvm.org/docs/AddressSanitizer.html)). ASan cannot share a process with Valgrind/Kvasir, so it has to live in a separate replay binary rather than in the build Daikon traces.

| Build | Flags | Purpose | Catches abs_diff? |
|---|---|---|---|
| Kvasir/Daikon (existing) | `-O0 -g -fwrapv` | Learn invariants, guidance | No: wrap is defined |
| Oracle (new) | `-O0 -g -fsanitize=address,undefined -fno-sanitize-recover=all`, no `-fwrapv` | Report bugs on replay | Yes, at `file:line:col` |
| Optional clang extra | add recoverable `-fsanitize=unsigned-integer-overflow,implicit-conversion` | Low-severity log | n/a (signed case) |

## An overflow alone is weak evidence; one that reaches a size or index is strong

Signed overflow is formally a bug in C, so Tier 1 is easy. Broader "did any arithmetic wrap?" detection runs into the field's most consistent finding. IOC found **219 static overflow sites in SPEC CINT2000** (148 unsigned, 71 signed), mostly hashing (128), overflow checks that rely on `-fwrapv` (37), bit manipulation (25) and RNGs (6). Its authors concluded that "the vast majority of overflows found (both unsigned and signed) were not bugs", and that "occurrence of integer overflow by itself is not a good indicator of a security vulnerability" ([Dietz et al.](https://users.cs.utah.edu/~regehr/papers/overflow12.pdf)). SmartFuzz, which generated tests on x86 binaries, says the same thing: "many overflows are benign and harmless". It reported only inputs that Valgrind or a crash confirmed, which yielded about 77 distinct bugs in 864 compute-hours ([Molnar et al., USENIX Sec 2009](https://people.eecs.berkeley.edu/~daw/papers/smartfuzz-use09.pdf)).

The later tools mostly differ in how they filter. **IntFlow** reports only overflows tied to untrusted input and cut false positives by **89%** compared with plain instrumentation ([Pomonis et al., ACSAC 2014](https://www3.cs.stonybrook.edu/~mikepo/papers/intflow.acsac14.pdf)). **IntPatch** checks only on paths that reach allocation or indexing sinks. It caught all 46 known overflow-to-buffer-overflow bugs in its suite, found 21 new ones, and costs about 1% overhead ([Zhang et al., ESORICS 2010](https://llvm.org/pubs/2010-09-ESORICS-FixOverflows.html)). IntTracker tags an overflowed value as "dirty" and reports only if the tag reaches a sink ([ACM](https://dl.acm.org/doi/10.1145/2714576.2714605)). A 2021 paper moves the check to just before the sensitive operation, which respects the program's own sanitization code, reports no false positives, and costs 1.75x ([Huang, ARES 2021](https://facsrv.cs.depaul.edu/zhuang28/ARES2021.pdf)). **KINT** and **IntScope** are static or symbolic tools, not run-time oracles. KINT found more than 100 integer errors in Linux, lighttpd and OpenSSH by constraint solving ([Wang et al., OSDI 2012](https://www.usenix.org/conference/osdi12/technical-sessions/presentation/wang)). IntScope runs symbolic execution plus taint tracking on x86 binaries and found more than 20 zero-day overflows in QEMU, Xen and others ([Wang et al., NDSS 2009](https://web.cse.ohio-state.edu/~lin.3021/ndss09.html)). They are useful as one-off audits, but they do not fit inside a per-input loop. For us this gives two tiers. **Tier 1** always reports signed-overflow UB, shift UB and divide-by-zero. **Tier 2** reports unsigned wrap or truncation only when the result reaches a `malloc` size, an array index, a pointer offset or a `memcpy` length.

## Steering toward overflow plugs straight into our distance machinery

An oracle only fires if some input actually overflows, and coverage alone rarely pushes operand values to the extremes. Three research lines turn the overflow condition itself into a target. **SAVIOR** labels every UBSan check as a potential bug, scores seeds by how many labels sit behind their unexplored branches (decayed by e^(−0.05·failures)), and solves the check condition with an SMT solver. It found bugs **43.4% faster than Driller** and 44.3% faster than QSYM, and its first 24 hours produced 481 UBSan violations, of which 243 were real bugs ([Chen et al., S&P 2020](https://arxiv.org/abs/1906.07327)). **ParmeSan** obtains targets by diffing a sanitized build against an unsanitized one, then directs the fuzzer toward them. It was 37% faster than Angora and 288% faster than AFLGo, and with UBSan targets it triggered a libpng integer overflow in an average of 32 minutes, an order of magnitude faster than with other sanitizers' targets ([Österlund et al., USENIX Sec 2020](https://download.vusec.net/papers/parmesan_sec20.pdf)).

The closest match to our design is **AFL-HR's "headroom"**. At every `+`, `−` and `*`, it computes the result in 64 bits and records how close it came to `INT_MAX`, as h = (INT_MAX + 1 − value)/INT_MAX, clamped to 0 on overflow. It keeps a second population of inputs that "don't reach new code regions, but reduce headroom". On 177 SV-COMP overflow benchmarks, it found **143 in the first 15 seconds versus 110 for AFL**, at a mean of **7 s per bug versus 42 s for AFL** and 27 s for AFLGo. All three tools converged to about 147 by 900 s ([Medicherla et al., SBST 2020](https://www.csa.iisc.ac.in/~raghavan/ReadingMaterial/sbst20.pdf)). Our fuzzer already keeps inputs that move closer to violating a Daikon invariant. Headroom is the same idea with a built-in invariant that exists for every arithmetic operation whether or not Daikon proposed it: `INT_MIN ≤ a op b ≤ INT_MAX`. libFuzzer's value profile is a generic, weaker relative. It hashes how close comparison operands are, at up to a 2x slowdown and a corpus several times larger ([libFuzzer docs](https://llvm.org/docs/LibFuzzer.html)). The speed-up holds early and fades with time, so headroom matters most for our short, single-seed runs.

## Template-free anomaly profiles would have flagged abs_diff without Daikon

Some bugs, such as wrong results or logic errors, are not undefined behaviour and no sanitizer defines them. For those, two older ideas fit our loop better than Daikon's per-round re-learning. **DIDUCE** keeps a per-expression value and a bitmask of the bits that have always been constant. The first value that flips a constant bit is reported, and the mask is then relaxed: a violation means `(new xor V) & M != 0`, followed by `M := M & ~(new xor V)`. It ranks reports by the drop in confidence, computed as evaluations / 2^(free bits). It costs about 3 words per tracked expression ([Hangal & Lam, ICSE 2002](https://cs.fit.edu/~pkc/id/related/hangal-icse02.pdf)). It found 2 otherwise-undetected bugs and the root causes of 3 more. After training, "almost all the violations detected after an hour … were interesting", although the authors give no numeric false-positive rate (same source). **CBI**'s `returns` scheme records, at every call site that returns a scalar, whether the result was ever `<0, <=0, >0, >=0, ==0, !=0` ([Liblit et al., PLDI 2005](https://pages.cs.wisc.edu/~liblit/pldi-2005/pldi-2005.pdf)). If every `abs_diff` return had been non-negative, its sign bit would be pinned, and the first wrapped result would fire with a large confidence drop. No `return >= 0` template needs to exist. Because the profile only ever relaxes, it never "forgets" in the way Daikon's re-learning does. The limitation is real: if a legitimate negative return was seen first, there is nothing to flag.

These profiles are noisy without filters. **Eclat** shows the useful one. It labels an input "fault-revealing" only when entry conditions hold but exit conditions are violated. That raised precision from **2.3% for unfiltered generated inputs to 30%** for the selected ones, which still means about 70% of reports were not real faults ([Pacheco & Ernst, ECOOP 2005](https://homes.cs.washington.edu/~mernst/pubs/classify-tests-ecoop2005.pdf)). For us there is a twist. Entry invariants learned from one seed (`a == 5`) would wrongly label every fuzzed input "illegal", so the alarm should key on exit and return values only. On the guidance side, InvsCov folds invariant violations into edge coverage and found **147 bugs versus 94 for plain coverage**, with 43 of its unique bugs at locations that coverage reached without triggering them ([Fioraldi et al.](https://www.usenix.org/system/files/sec21-fioraldi.pdf)). Binvariants applies the same idea to registers in binaries and traced 18 bugs on 25 binaries to distinct invariant violations ([Yang & Nagy, FSE 2026 slides](https://futures.cs.utah.edu/papers/26FSE-c_slides.pdf)). Halo uses invariant inference to approximate the path condition to a target and reports a 15.3x speedup to the same bug ([Huang et al., S&P 2024 slides](https://nebelwelt.net/files/24Oakland2-presentation.pdf)). Both are guidance tools, not detectors.

**Differential and metamorphic oracles** cover the remaining gap. In a differential oracle, two implementations of the same function cross-check each other ([NEZHA, S&P 2017](https://www.ieee-security.org/TC/SP2017/papers/390.pdf)). Our cheapest version is to run each input on the `-fwrapv` build and on the sanitizer build and treat a divergence in outcome as the report, or to compare a small arithmetic function against a Python big-integer evaluation. A metamorphic relation is a property stated once, such as `f(a,b) == f(b,a)` or `f(a,b) >= 0`. Differential oracles miss bugs that both sides share ([DBMS fuzzing survey](https://arxiv.org/pdf/2311.06728)), and they generate triage work from legitimately unspecified behaviour ([arXiv 2601.15074](https://arxiv.org/pdf/2601.15074)). LLM-proposed invariants, as in LISA, are emerging, but they are reported as "high-confidence bug candidates" that a developer still has to confirm ([arXiv 2607.18711](https://arxiv.org/abs/2607.18711)).

| Approach | Catches | Cost | False positives | Fit for our loop |
|---|---|---|---|---|
| UBSan oracle build (no `-fwrapv`) | Signed overflow, shift, div-by-0, bounds | ~44% mean (IOC) | "Not expected" for UB | Source: top priority |
| ASan replay | Heap/stack/global OOB, UAF | ~2x | "Not expected" | Source: same replay pass |
| Sink-gated unsigned checks (IntPatch-style) | Overflow → buffer overflow | ~1% | Low | Source, Tier 2 |
| AFL-HR headroom | Finds overflows faster (7 s vs 42 s per bug) | 64-bit shadow compute | n/a (guidance) | Reuses our distance code |
| DIDUCE/CBI return profile | Novel sign or bit changes, logic bugs | O(1) per call | Unquantified, ranked | Both modes |
| Differential / metamorphic | Wrong results | One extra run | Triage of spec gaps | Small functions |
| SAVIOR/ParmeSan targeting | Reaching checks | Solver or IR diff | n/a (guidance) | Later, if needed |

## In blackbox mode, the overflow flag works but lazy mapping must go

A stripped binary cannot be recompiled with sanitizers, so the checks have to come from the emulator. The CPU already computes the signal we need. IOC's "flag postcondition" checks read the processor's overflow flag after each arithmetic operation ([Dietz et al.](https://users.cs.utah.edu/~regehr/papers/overflow12.pdf)). The local Unicorn 2.1.4 test in our notes confirmed that EFLAGS.OF (bit 11) is set after `sub eax,[rbp-8]` on the `abs_diff` object. It also exposed a trap. The preceding `cmp eax,[rbp-8]` sets OF for the same operands, and OF stays set through later `mov` and `jmp` instructions. A naive "OF is 1" rule therefore fires on the wrong instruction. The correct rule is to remember the previous instruction in the code hook and read OF only when that instruction was a flag-writing arithmetic one (`add`, `sub`, `imul`, `neg`, `inc`, `dec`, `adc`, `sbb`), never `cmp`. These notes also suggest, without testing, a few design refinements. A 32-bit OF means `int` overflow; a 64-bit OF at `-O0` is usually pointer arithmetic and should be ranked lower. `lea`-based additions set no flags, which matters at `-O1` and above but rarely at `-O0`. A carry-flag (CF) hit alone is low priority, because the binary does not say whether the C type was unsigned. And IOC's finding that most wraps are intentional applies even more strongly here, so a per-PC allowlist and a sink-reachability filter are worth adding. Cost is the open question. AFL++ measures DBI tools such as DynamoRIO and Pin at a 98–99.5% speed loss for coverage ([AFL++ binary-only doc](https://raw.githubusercontent.com/AFLplusplus/AFLplusplus/stable/docs/fuzzing_binary-only_targets.md)), and we have not measured a per-instruction Python hook in Unicorn.

Memory bugs are the bigger hole. The tracer maps a fresh page whenever the target touches unmapped memory, which turns every wild read or write into a silent success. That removes the one oracle that emulation provides for free. The binary-only alternatives each have a cost. **BaseSAFE** builds a heap sanitizer from Unicorn's own memory hooks. It places a hooked canary region between heap chunks, re-hooks freed chunks so that "all use-after-free bugs are detected", and zeroes size fields to catch double-frees. Its only stated miss is a write that skips the canary and lands in another live chunk ([Maier et al., WiSec 2020](https://arxiv.org/pdf/2005.07797)). QASan adds about 1.61x on top of QEMU-mode fuzzing ([QASan repo](https://github.com/andreafioraldi/qasan)). libdislocator's guard pages are cheaper but "can catch less bugs" and need dynamic linking ([AFL++ libqasan README](https://raw.githubusercontent.com/AFLplusplus/AFLplusplus/stable/qemu_mode/libqasan/README.md)). Valgrind memcheck costs 20–30x and "can't detect out-of-range reads or writes to arrays that are allocated statically or on the stack" ([Valgrind Quick Start](https://valgrind.org/docs/manual/quick-start.html)). In our local test it also reported nothing for `abs_diff`, since it has no integer checks. BaseSAFE's design is the natural fit, because our tracer already runs on Unicorn and already models allocation.

## A prioritized plan for our loop

The order below puts precise, cheap oracles first, then guidance, then the noisier anomaly signals. Each step adds a *report* channel that runs alongside invariant refutation and does not depend on it. That is the structural change the `abs_diff` miss calls for.

To check that steps 1 and 3 work, rerun the original single-seed `abs_diff` configuration and confirm one deduplicated overflow report per mode. Then measure throughput with and without the Unicorn flag hook, since that cost is the one number we do not yet have.

## Conclusion

The `abs_diff` miss was not a Daikon bug. We asked a derived oracle to do an implicit oracle's job, and `-fwrapv`, which keeps Kvasir's view of arithmetic sane, also turned off the one check that would have fired. Once detection is separated from learning, the invariants return to what the literature shows they do well: steering the fuzzer (InvsCov, Halo) and explaining a failure after something precise has flagged it (ClearView). A sanitizer replay build and an OF-flag hook supply that precise signal. The headroom distance and a never-forgetting return profile catch the cases where the input never quite overflows or the bug is not undefined behaviour.

Two questions remain open, and both should be measured on our targets rather than assumed. The first is how noisy OF-flag and sign-flip alarms are in practice: no source we found quantifies false-positive rates for either during greybox fuzzing, and IOC's results predict that intentional wraparound will dominate in real binaries. The second is what a per-instruction Python hook costs in Unicorn. The answers decide whether the blackbox oracle runs on every input or only on replays of new-coverage inputs.
